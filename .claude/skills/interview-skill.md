# Interview Skill

사용자의 아이디어를 심층 인터뷰하여 명확한 사양서로 변환하는 워크플로우.

## 핵심 원칙

**절대 즉시 코딩하지 않는다.** 모든 주요 결정을 인터뷰로 확정한 후에만 구현 단계로 진입.

## 인터뷰 프로세스

### Phase 1: 초기 이해 (1-2 질문)

1. "어떤 문제를 해결하려고 하시나요?" (핵심 목적)
2. "주요 사용자는 누구인가요?" (타겟)

### Phase 2: 기능 범위 (2-4 질문)

1. "필수 기능(MVP)은 무엇인가요?"
2. "나중에 추가할 기능이 있나요?"
3. "비슷한 서비스 중 참고할 만한 것이 있나요?"

### Phase 3: 기술 요구사항 (2-4 질문)

1. "선호하는 기술 스택이 있나요?"
2. "기존 시스템과 연동이 필요한가요?"
3. "성능/보안 요구사항이 있나요?"
4. "배포 환경은 어디인가요?"

### Phase 4: 제약조건 (1-2 질문)

1. "예산이나 일정 제약이 있나요?"
2. "반드시 피해야 할 것이 있나요?"

## 인터뷰 규칙

- 한 번에 1-2개 질문만 던진다 (사용자 피로 방지)
- 맥락에 맞는 질문만 선택한다 (모든 질문을 다 할 필요 없음)
- 후속 질문으로 깊이 파고든다
- 답변이 모호하면 구체적 예시를 요청한다
- 충분한 정보가 모이면 확인 요약을 제시한다

## 역할(Persona) 모드

사용자가 특정 관점을 요청하면 해당 전문가 시각으로 인터뷰:

| 요청 | 인터뷰 초점 |
|------|-------------|
| "보안 관점" | 인증, 권한, 데이터 암호화, 취약점 |
| "비용 관점" | 인프라 비용, 운영 비용, 확장성 |
| "UX 관점" | 사용자 플로우, 접근성, 반응성 |
| "성능 관점" | 응답 시간, 동시 접속, 캐싱 전략 |

## 사양서 출력 형식

인터뷰 완료 후 다음 구조로 SPEC.md 생성:

```markdown
# [프로젝트명] 사양서

## 1. 개요
- 목적:
- 타겟 사용자:
- 핵심 가치:

## 2. 기능 요구사항

### 2.1 필수 기능 (MVP)
- [ ] 기능 1
- [ ] 기능 2

### 2.2 추가 기능 (Phase 2)
- [ ] 기능 A
- [ ] 기능 B

## 3. 기술 스택
- Frontend:
- Backend:
- Database:
- Infrastructure:

## 4. 비기능 요구사항
- 성능:
- 보안:
- 확장성:

## 5. 제약조건
- 일정:
- 예산:
- 기술적 제약:

## 6. 결정 사항 요약
| 항목 | 결정 | 근거 |
|------|------|------|
| ... | ... | ... |
```

## 워크플로우 예시

```
사용자: "로그인 기능 인터뷰 시작해줘"

Claude: "로그인 기능을 구현하시려는군요. 몇 가지 질문으로 요구사항을 정리하겠습니다.

1. 어떤 인증 방식을 고려하고 계신가요?
   - 이메일/비밀번호
   - 소셜 로그인 (Google, Kakao 등)
   - SSO/OAuth"

사용자: "이메일/비밀번호랑 카카오 로그인 둘 다 필요해요"

Claude: "알겠습니다. 추가 질문입니다.

2. 비밀번호 정책이 필요한가요? (최소 길이, 특수문자 등)
3. 로그인 실패 시 계정 잠금 기능이 필요한가요?"

... (인터뷰 계속) ...

Claude: "지금까지 내용을 정리하면:
- 인증: 이메일/비밀번호 + 카카오 OAuth
- 비밀번호: 8자 이상, 특수문자 1개 이상
- 보안: 5회 실패 시 10분 잠금
- JWT 토큰 사용, 7일 유지

이 내용으로 사양서를 작성할까요?"
```

## 인터뷰 종료 조건

다음 중 하나 충족 시 사양서 작성 제안:

- 모든 Phase의 핵심 질문에 답변 완료
- 사용자가 "충분해요" 또는 "이 정도면 됐어요" 표현
- 명확한 MVP 범위가 정의됨

## 사양서 작성 후

사양서 확정 후 사용자에게 선택지 제공:

1. "사양서 기반으로 구현을 시작할까요?"
2. "수정하고 싶은 부분이 있나요?"
3. "추가 인터뷰가 필요한 영역이 있나요?"
